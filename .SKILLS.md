# Writing and finding a memory

## Give a record an address

The folder templates extend one envelope. Use UTF-8 Markdown, a YAML frontmatter block, and a short title that makes sense in search results. Expand placeholders before committing. Use a plural folder name and singular `kind` as in the [vault map](.README.md). The root uses kind `orientation` and folder token `.`.

| Property | Rule |
| --- | --- |
| `schema` | Integer version of this kind's format, initially `1`. Each reader explicitly supports a set of versions. |
| `id` | Globally unique `<kind>-<lowercase UUID>`. The filename is `<id>.md`. Once committed, the ID and path persist. |
| `recorded_at` | Quoted UTC timestamp for the creation of this version. A sensor timestamp belongs in its own field with its clock domain. |
| `sources` | YAML list of quoted wikilinks to the actual direct inputs, such as `"[[percepts/percept-<uuid>]]"`. Empty is valid for firsthand acquisition or an originating operator request. Derived records identify their evidence. |
| `supersedes` | Optional single quoted link to the preceding version of the same kind. A newer measurement usually adds evidence and has its own identity. |
| `also_supersedes` | Optional list of other heads reconciled by the same correction. Requires `supersedes`. Every target must be a distinct head of the same lineage at review time. |

Links to root records omit the folder prefix. Multiple observations of a thing may disagree. Keep those observations addressable, identify their common ancestors, and describe the disagreement in the claim. To find current heads, follow the reverse of both supersession properties until no successor exists. If a record has two successors, return both current heads. To reconcile them, a reviewer reads both, writes the resolved account and its reasons, and names one head in `supersedes` and the other in `also_supersedes`. All supersession links lead to previously committed versions of the same kind and lineage. A correction to an input flags its dependents for review through backlinks. Their original citations keep pointing to the version used.

For live input, allocate an ID when accepting the event and keep it with the pending write. For replayable work, derive a UUIDv5 in namespace `58664475-41a0-4770-949f-fa9427ad0cea` from the kind, producer/rule version, and stable input keys. Each producer defines the key and preserves meaningful order. Store the proposed bytes and timestamp until the write is acknowledged, or recover the already committed record by ID before constructing a retry. Recording time alone cannot distinguish a retry from a new event.

## Follow evidence in either direction

1. Start with a question, a phrase, or a known ID. Search notes in the relevant folders. A question about camera motion starts with attempts, while a question about the object's identity starts with percepts or beliefs.
2. Open the matching current records. Follow `sources` backwards to the actual observations and check scope, event time, frame, and access to the payload. If two claims rest on the same image, count that image once. A gap may leave the question open.
3. Follow backlinks to find consequences, counterevidence, or a correction. Bring the relevant evidence into the answer with its links and say what remains uncertain. When a search is truncated or the index is incomplete, keep that qualification with the answer.
4. When a task pauses, optionally commit an orientation note linking the records needed to resume it. When resuming, follow their successors, check expiry, and re-evaluate outstanding work.

## Recover after interruption

Subscribe to commit notices before scanning ordinary committed notes. Process the scan and queued notices by ID. Repeat the scan periodically to catch missed deliveries. Consumers filter by kind, validate the supported schema, and remember completed derivations by input key. Failed dependencies stay pending. An unfamiliar schema is reported with the affected path and held for a compatible reader. Other records remain readable.

The writer publishes a Markdown note only after validating its references and installing its assets. A partial write stays outside the note graph. A missing or damaged asset discovered later is recorded as unavailable, along with the reason if known. Authors submit corrections as new linked notes. The vault keeps the source and current reading available for the next inquiry.
