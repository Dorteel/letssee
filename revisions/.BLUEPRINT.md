# Reviewing an architectural change

The node `/reflection/reviewer` reads committed notes in the vault and implements a proposed `mind_interfaces/srv/ReviewHabit` service at `/reflection/review`. An operator initiates review when a question warrants the work. The request contains `string target` (the rule under review) and `string[] example_ids` (committed examples). The response contains `bool ok`, `string proposal_id`, and `string detail`. The node validates a bounded set of inputs and commits a proposal synchronously. It returns the existing proposal for an identical review key. If the examples cannot support a testable proposal, it returns the reason with an empty ID.

| Parameter | Type and default | Use |
| --- | --- | --- |
| `max_examples` | integer, `16` | Largest number of distinct examples per request. Reject a larger request with its limit. |
| `review_rule_version` | string, `"1"` | Identifies the review rule in the proposal derivation key. |

The derivation key includes the review rule version, target, baseline and candidate references or proposal fingerprint, and the sorted example IDs. The node depends on the shared vault reader, `/vault/commit`, and a versioned record of the active rules. It can use `/vault/recall` to locate related cases. Every cited example must resolve to a readable note. A dangling source yields a failed request with the affected ID.

Trial runs use an isolated vault copy and a separate ROS domain without a body connection. A trial reviewer brings the outcome back through `/vault/commit` as a new revision note with links to the original input IDs and proposal. A maintainer reviews it, deploys an accepted version through the normal release process, and records the actual release identifier. Commit notices let interested readers refresh their indexes. A note alone carries no authority to deploy a rule. A rollback uses the same decision format and records the restored version.
